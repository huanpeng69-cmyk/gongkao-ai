# 用户数据存储决策

## 背景

旧版本把账号、密码校验信息、答题记录、错题本和统计数据全部写入浏览器 `localStorage`。这会导致数据容易被同源脚本读取、换设备无法同步，也不适合客户现场的多人使用场景。

## 决策

从 2026-09-09 起，Node 服务端负责保存用户数据和会话：密码使用 Node `scrypt` 加盐哈希，登录状态使用 HttpOnly Cookie，会话和用户数据写入服务端数据目录。前端只在内存中持有当前用户数据，`localStorage` 仅保留非敏感的用户展示信息和界面偏好。

当前实现使用无新增原生依赖的 JSON 文件存储，数据目录由 `GONGKAO_DATA_DIR` 配置，并已加入忽略规则。API 与存储实现分离，后续可将 `lib/server/store.ts` 替换为 SQLite、MySQL 或 PostgreSQL 适配器，而不改变前端接口。

## 备选方案

- 继续使用 `localStorage`：实现成本最低，但没有服务端安全、同步和多用户能力。
- 只加密 `localStorage`：密钥仍在浏览器端，无法解决恶意脚本读取和换设备问题。
- 直接引入正式数据库：长期更适合生产，但需要先确定客户环境、数据库类型和持久化部署方式。

## 迁移与边界

旧浏览器账号首次通过服务端登录时，会尝试把对应的旧学习数据上传到服务端；旧数据暂不自动删除，作为迁移失败时的本地回滚材料。GitHub Pages 等静态托管没有这些 API，必须使用 Node 服务或正式数据库部署版本。
