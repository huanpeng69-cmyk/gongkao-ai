# 用户数据存储决策

## 背景

旧版本把账号、密码校验信息、答题记录、错题本和统计数据全部写入浏览器 `localStorage`。这会导致数据容易被同源脚本读取、换设备无法同步，也不适合客户现场的多人使用场景。

## 决策

从 2026-09-09 起，Node 服务端负责保存用户数据和会话：密码使用 Node `scrypt` 加盐哈希，登录状态使用 HttpOnly Cookie，会话和用户数据写入服务端数据目录。前端只在内存中持有当前用户数据，`localStorage` 仅保留非敏感的用户展示信息和界面偏好。

当前实现使用无新增原生依赖的 JSON 文件存储，数据目录由 `GONGKAO_DATA_DIR` 配置，并已加入忽略规则。API 与存储实现分离，后续可将 `lib/server/store.ts` 替换为 SQLite、MySQL 或 PostgreSQL 适配器，而不改变前端接口。

## 备选方案

- 继续使用 `localStorage`：实现成本最低，但没有服务端安全、同步和多用户能力。
- 只加密 `localStorage`：密钥仍在浏览器端，无法解决恶意脚本读取和换设备问题。
- 直接引入正式数据库：长期更适合生产，但需要先确定客户环境、数据库类型和持久化部署方式。

## 迁移与边界

旧浏览器账号首次通过服务端登录时，会尝试把对应的旧学习数据上传到服务端；旧数据暂不自动删除，作为迁移失败时的本地回滚材料。GitHub Pages 等静态托管没有这些 API，必须使用 Node 服务或正式数据库部署版本。

## 加固记录（F4：读取失败不得被当作空库）

**问题**：`lib/server/store.ts` 的 `readDatabase` 曾用 `catch { return emptyDatabase() }` 兜底，把「文件损坏 / 瞬时 I/O 错误 / 结构非法」全部降级成空库。配合写前重读（read-modify-write），只要某次读取失败，紧随其后的任意一次写入就会把整库覆盖成近空库——静默且不可逆。差分消融复现：磁盘文件完好、仅一次瞬时读失败时，旧实现即把既有用户与其数据清空。

**加固**：

- 只有 `ENOENT`（首次运行尚无文件）才返回空库；解析失败、结构非法、其它 I/O 错误一律抛出。`withFreshDb` 因此不执行变更、不落盘，损坏文件原样保留待人工恢复（fail-closed）。
- 覆盖前滚动备份 `users.json.bak`（best-effort），作为最后可恢复兜底。
- `writeQueue` 以 `run.then(() => {}, () => {})` 续接，确保一次失败不会把后续所有写入永久毒化。

**代价与恢复**：数据库损坏时，读取类接口会返回 500（不再假装空库），这是有意的 fail-closed。恢复方式：用同目录 `users.json.bak` 覆盖回 `users.json` 后重启。

**防再犯检查（不变量）**：任何「读取 → 改写 → 覆盖」的持久化路径，都必须区分「文件不存在」与「文件读不到/读坏了」，禁止用 catch-all 把读取错误降级为空值再写回；覆盖前必须留可恢复副本。回归测试：`npm test`（`scripts/verify-store.mjs`，纯 Node 无框架，转译真实 `store.ts` 断言上述不变量）。
## 已知残留（F1：跨进程并发写）

**现状**：`withFreshDb` 的 `writeQueue` 只在「同一 Node 进程内」串行化。多进程/多实例共享同一数据文件时，仍存在经典的读-改-写交错丢更新：P1 读 → P2 读 → P1 写 → P2 写（P2 基于陈旧读覆盖 P1）。

**为何暂不修**：

- 该项目单机自用 / 客户现场单实例部署下，同一数据目录只被一个 Node 进程打开，队列已足够。
- 文件锁只在「多进程确实共享同一文件系统」时才有意义。若部署到 Vercel 这类无共享盘的多副本环境（见 `2026-09-09-mobile-deployment.md`），进程各自有独立 FS，文件锁不但无效，JSON 文件存储本身就不成立——此时正确的解是换成真正的共享数据库，而非补锁。

**触发条件（满足其一即须升级为正式数据库，不要再补文件锁）**：

- 服务端以多副本 / 多实例对外提供服务（Serverless、K8s 多副本、PM2 cluster）。
- 需要多台机器共享同一份账号与学习数据。

**防再犯检查**：引入多副本前，先确认存储后端具备「跨实例共享 + 读写一致」能力；否则 `saveUserData` / 注册 / 登录会随机丢数据或读不到，且难以复现。
